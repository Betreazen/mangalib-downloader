# PRD — миграция на Tauri + Rust

## 1. Проблема / мотивация

Текущий стек — Python 3.14 + PySide6 + httpx + Pillow. Работает, но:

- **Размер и распространение.** PyInstaller-сборка ~55 МБ, требует `--collect-all PIL`
  для AVIF, тяжёлый старт. Tauri-бинарь — единицы МБ, нативный старт.
- **Производительность I/O-fan-out.** Мультисорс опрашивает ~10 сайтов параллельно
  и качает сотни страниц. Rust + tokio даёт предсказуемую параллельность без GIL.
- **AVIF/обработка картинок.** Сейчас зависит от Pillow 12 + плагин. В Rust —
  крейт `image` с AVIF, статически, без внешних кодеков.
- **Один бинарь без рантайма.** Не нужен установленный Python у пользователя.

> **Важно (не-цель):** это НЕ переписывание ради переписывания. Ядро на Python
> уже рабочее. Миграция оправдана дистрибуцией и параллельностью, а её главный
> риск — регресс несущего мультисорс-контракта. Поэтому паритет поведения —
> критерий №1.

## 2. Цели

- **G1. Паритет функций** с текущим приложением: поиск по всем сайтам, выбор
  самого актуального источника, выбор перевода (ветки), скачивание глав,
  конвертация AVIF→JPG, упаковка CBZ, докачка, защита от лимитов.
- **G2. Мультисорс в UI** (сейчас есть только в CLI): поиск по всем сайтам из окна,
  показ «чей перевод, сколько глав», авто-выбор лучшего источника.
- **G3. Кастомные инструменты тестирования** (ключевое требование): режим
  «тест одного сайта», dev-панель, харнессы — см. TESTING.md.
- **G4. Один самодостаточный бинарь** на Windows (позже — macOS/Linux).
- **G5. Захват токенов** источников из встроенного вебвью (аналог текущего
  `token_window`), для dev; прод-путь — мастер-аккаунты.
- **G6. Кроссплатформенность: Windows + Android** на v1. Один Rust- core и один
  Svelte-фронт, две цели сборки (desktop-бинарь + APK). iOS — потом, не сейчас.

## 3. Не-цели

- Не меняем предметную логику (перевод = `branch_id`; «актуальнее» = больше
  уникальных глав по `(том, номер)`). Это переносится 1:1.
- Не реализуем в рамках миграции новые сайты-заглушки — переносим текущий набор
  адаптеров; заглушки остаются заглушками.
- **iOS на v1 не делаем** (Tauri его поддерживает — оставляем на потом).
- Не делаем синхронизацию облака, встроенную читалку — только загрузчик.
- Не трогаем формат вывода на диск на desktop (та же раскладка `original/`,
  `converted/`, CBZ). На Android раскладка та же, но корень — в разрешённом
  scoped-storage / выбранной пользователем папке (см. ARCHITECTURE §11).

## 4. Пользователи и сценарии

- **Владелец (ты).** Ищет тайтл → приложение находит по всем сайтам → показывает,
  где перевод полнее → качает оттуда. Плюс: как разработчик — прогоняет per-site
  тесты, ловит токены новых сайтов через встроенный браузер.
- **Конечный пользователь (прод).** То же, но токены сайтов уже вшиты через
  мастер-аккаунты — регистрироваться нигде не нужно.

## 5. Критерии успеха (Definition of Done)

- **DoD-1.** Для 5 эталонных тайтлов результат мультисорс-поиска и выбор best
  совпадают с Python-версией (те же источники, те же числа глав ±0).
- **DoD-2.** Скачивание главы с каждого `verified`-источника даёт те же файлы
  (тот же список страниц, корректный формат) — проверяется per-site харнессом.
- **DoD-3.** Конвертация AVIF→JPG и CBZ идентичны по составу (имена/кол-во).
- **DoD-4.** Защита от лимитов: на 429/Retry-After поведение как в Python
  (ретраи, паузы) — проверяется на mock-сервере.
- **DoD-5.** Dev-панель «тест одного сайта» запускается (флагом/режимом) и
  прогоняет search→chapters→pages→download для выбранного источника.
- **DoD-6.** Бинарь Windows собирается и запускается на чистой машине без Python.
- **DoD-7.** `cargo test` (офлайн, на фикстурах) зелёный; `--features live`
  прогоняет per-site smoke.
- **DoD-8 (Android).** APK собирается, ставится на устройство/эмулятор; поиск →
  выбор тайтла → скачка → файлы в разрешённой папке. Мультисорс-поиск и per-site
  тест-панель работают в мобильной сборке.

## 6. Риски и смягчение

| Риск | Влияние | Смягчение |
|------|---------|-----------|
| Регресс парсеров при порте | Высокое | Golden-фикстуры из реальных ответов Python-версии; diff-тесты |
| AVIF-декод в Rust отличается от Pillow | Среднее | Сравнение байт/размеров на эталонных страницах в DoD-3 |
| **AVIF-декод на Android** (dav1d/NDK-кросс-компиляция) | Высокое | Проверить `image`+`dav1d` под NDK на Фазе 1b; fallback — на мобиле хранить оригинал AVIF без конвертации (Android умеет его показывать), конвертацию сделать опциональной |
| **Android scoped storage** — нельзя писать произвольный путь | Высокое | Абстракция хранилища (ARCHITECTURE §11): desktop = прямой путь, Android = app-dir / SAF-папка через плагин |
| **Фоновая скачка на Android** может убиваться ОС | Среднее | Foreground-service/keep-awake на время скачки; чанковать; докачка (skip-existing) уже есть в логике |
| Захват Bearer из вебвью на desktop+Android | Среднее | Единый путь: webview + JS-чтение localStorage/cookie (см. решение D3) — работает на обеих платформах |
| HTML-скрапинг (mangahub) хрупок при порте регэкспов | Среднее | Перенести как есть, фикстуры HTML, отметить `verified-fragile` |
| Сайты меняются во время миграции | Низкое | `doctor` health-чек + фикстуры замораживают контракт для тестов |
| Объём работы (10+ адаптеров × 2 платформы) | Среднее | Ядро одно на обе платформы; адаптеры платформонезависимы; фазы пачками |

## 7. Решения (зафиксированы заказчиком 2026-07-18)

- **D1. Фронтенд — Svelte 5 + TypeScript + Vite.** Один фронт на desktop и Android
  (адаптивная вёрстка). Виртуализация длинных списков глав.
- **D2. Целевые ОС v1 — Windows + Android.** iOS отложен. Один Rust-core, две
  цели сборки. См. ARCHITECTURE §11 (мобильные особенности).
- **D3. Захват токенов — один путь: встроенный webview + чтение `localStorage`/
  cookie через JS-eval** (проще и одинаково работает на desktop и Android;
  перехват HTTP-заголовков как отдельный путь НЕ делаем — лишняя платформенная
  сложность). Прод — мастер-аккаунты через конфиг/ENV.
- **D4. Python-версия остаётся рабочим эталоном** до закрытия паритет-чеклиста,
  затем архивируется в тег/ветку (не удаляется).
