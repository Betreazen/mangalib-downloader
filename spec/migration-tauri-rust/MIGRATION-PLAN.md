# MIGRATION-PLAN.md — план перехода, паритет, откат

## Стратегия

**Strangler-переход, а не «большой взрыв».** Python-версия остаётся рабочим
эталоном, пока Rust не закроет паритет-чеклист. Мигрируем снизу вверх: контракт →
движок → источники → GUI. На каждом шаге система собирается и запускается.

## Порядок по сообществам графа

graphify выделил сообщества — берём их как единицы работ, от ядра к периферии:

1. **Контракт/ошибки** (сообщества 5, 8: `MangaSource`, DTO, `SourceError`) → Фаза 1.
2. **Движок** (сообщество 1: downloader/packager/convert; rate-limit из 0/3) → Фаза 1.
3. **Агрегатор/реестр** (сообщество 6) → Фаза 2.
4. **Источники** (4: *Lib; 7: remanga/mangahub; 9: inkstory; 5: senkuro/mangadex/stubs)
   → Фазы 2–3.
5. **Хранилище/токены** (сообщество 11) → Фазы 2, 6.
6. **GUI/лаунчеры** (сообщества 2, 3) → Фаза 4 (переписываются на Svelte, не портируются).

Импорт-циклы, замеченные графом (`__init__ ↔ api/models`), при переносе устраняются
структурой `lib.rs` — отдельной работы не требуют.

## Паритет-чеклист (гейт закрытия миграции)

Сверка Rust ↔ Python на одинаковых входах:

- [ ] `search_all("berserk")` — те же группы и best (числа глав ±0) — DoD-1.
- [ ] `search_all` на 5 эталонных тайтлах (разные языки/типы) — совпадает.
- [ ] Для каждого `verified`-источника: список глав по эталонному тайтлу совпадает
      по количеству и номерам.
- [ ] Скачка 1 главы с каждого `verified`: тот же набор страниц, формат, раскладка.
- [ ] AVIF→JPEG: те же имена/количество в `converted/`; CBZ идентичны по составу.
- [ ] 429/Retry-After/ретраи: поведение как в Python (mock).
- [ ] Нормализация названий и выбор best: порт-тесты зелёные.
- [ ] «Грязные данные» (строка вместо объекта, 404 детали) не роняют разбор.
- [ ] Токен *Lib: пойман и применяется (18+/лицензия отдаёт главы).
- [ ] Бинарь Windows на чистой машине без Python — работает (DoD-6).
- [ ] APK ставится и работает на Android-устройстве/эмуляторе (DoD-8): поиск →
      тайтл → скачка → файлы в выбранной папке; мультисорс и per-site панель.
- [ ] AVIF на Android: конвертация ИЛИ оригинал-fallback (решение Фазы 1b) —
      страницы читаемы.

## Эталонные тайтлы для сверки (заморозить)

Подобрать по 1 на характерный случай (зафиксировать slug/id на старте):
- многосайтовый популярный (Berserk/Naruto) — проверка группировки/best;
- с несколькими ветками перевода на *Lib — проверка веток;
- лицензированный/18+ — проверка токена;
- HTML-источник (mangahub) — проверка скрапинга;
- meta-only (shikimori) — проверка `can_download=false`.

Ответы этих тайтлов записать в `fixtures/` (TESTING §4) — они же golden.

## Откат

- До Фазы 7 Python-версия — основная и рабочая; Rust собирается параллельно в
  `mangadl/`. Откат = просто продолжать пользоваться Python-версией.
- Каждая фаза атомарна и оставляет обе ветки рабочими; неудачную фазу откатываем
  по git без влияния на остальное.
- Python-код удаляем только после закрытия всего паритет-чеклиста (и то —
  переносим в архивную ветку/тег, не стираем).

## Оценка объёма (грубо, для планирования — не обязательство)

| Фаза | Относительный объём |
|------|---------------------|
| 0 каркас | S |
| 1 контракт+движок | M |
| 2 агрегатор+2 источника | M |
| 3 остальные источники | L (10+ адаптеров пачками) |
| 1b AVIF/NDK spike | S |
| 4 Tauri+фронт | L |
| 5 dev-тесты | M |
| 6 токены | M |
| 7 сборка Win+Android+паритет | M |

Самое ёмкое — Фаза 3 (много адаптеров) и Фаза 4 (новый UI). Их можно дробить на
независимые куски под саб-агентов **после утверждения этой спеки** (spec-pilot
Гард 2) — по одному источнику/экрану на агента, с общим контрактом из Фазы 1.

Android добавляет вес в Фазе 7 (SAF-хранилище, foreground-service, APK) и spike
1b (AVIF под NDK), но ядро и адаптеры платформонезависимы — двойной цели сборки
они не удорожают.

## Что НЕ делаем на миграции (вынести в бэклог)

- Реализацию сайтов-заглушек (отдельная задача после паритета).
- Новые фичи UI сверх текущих.
- Кроссплатформенную сборку, если PRD §7 решит «Windows-first».
