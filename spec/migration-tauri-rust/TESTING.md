# TESTING.md — кастомные инструменты тестирования

Главное требование заказчика: **тестировать скачку с каждого сайта по
отдельности** — через переключатель / особый режим запуска приложения — плюс
другие варианты тестирования. Ниже — полный набор инструментов, от GUI-режима до
CI. Спроектировано так, чтобы «сайт сломался» ловилось раньше пользователя.

## Обзор уровней

| # | Инструмент | Где | Сеть | Когда гоняем |
|---|-----------|-----|------|--------------|
| 1 | **Per-site тест-режим в GUI** (dev-панель) | Tauri | да | вручную, при работе над источником |
| 2 | **`doctor` — health-чек всех сайтов** | CLI + GUI-вью | да | перед релизом, периодически |
| 3 | **CLI тест-подкоманды** (`test-source`, `test-all`) | CLI | да | локально + CI (nightly) |
| 4 | **Golden-фикстуры (парсеры)** | `cargo test` | нет | каждый коммит / PR |
| 5 | **Mock-сервер (лимиты/ретраи/скачка)** | `cargo test` | нет (wiremock) | каждый коммит / PR |
| 6 | **IPC-контракт тесты** | `cargo test` | нет | каждый коммит / PR |
| 7 | **E2E смоук приложения** | Tauri/WebDriver | да | перед релизом |
| 8 | **Android: сборка + smoke на эмуляторе** | Gradle/emulator | да | перед релизом + при правках платформы |

Правило (в `CLAUDE.md`, слой verify из spec-pilot): *«Перед сдачей опиши, как
проверишь, затем запусти проверку»*. Офлайн-уровни (4–6) — обязательный гейт PR;
сетевые (1–3,7) — по требованию/nightly, чтобы флап сайтов не красил каждый PR.

## 1. Per-site тест-режим в GUI (ключевое)

### Как включается (несколько способов — «переключатель или режим запуска»)

- **Режим запуска:** `mangadl --mode site-test` или env `MANGADL_MODE=site-test` —
  приложение стартует сразу в QA-панели.
- **Сборка с фичей:** `cargo build --features devtools` — панель вшита; в релизной
  сборке без фичи её нет.
- **Горячий тумблер:** в dev-сборке — пункт меню/иконка «🧪 QA» + хоткей
  (напр. `Ctrl+Shift+D`) открывает панель поверх обычного UI.

### Что делает панель

Выпадающий **switcher источника** (все `id` из реестра) + поле запроса + кнопки:

- **Run full pipeline** — прогоняет для выбранного сайта:
  `search → (выбрать 1-й) → get_chapters → (выбрать 1-ю) → get_pages →
  download 1–3 страниц` и показывает **SiteTestReport**:
  - тайминги каждого шага (мс),
  - число найденных тайтлов / глав / страниц,
  - первые N URL страниц + **превью первой скачанной страницы** (визуально видно,
    что скачалось именно изображение, а не заглушка),
  - какой формат пришёл (AVIF/WebP/JPEG) и результат конвертации,
  - ветки перевода (branch_id/команды), если источник их отдаёт,
  - ошибки по шагам (locked/unreleased/auth/parse).
- **Search only / Chapters only / Pages only** — точечные шаги (быстрее при отладке).
- **Токен:** переключатель «с токеном/без» (для 18+/лицензий), берёт из `tokens.json`.
- **Save as fixture** — записать полученные ответы в `fixtures/<source>/` для
  офлайн-тестов (уровень 4). Так реальный ответ замораживается в golden.

Реализация: IPC-команда `dev_run_site_test(source_id, query, opts) -> SiteTestReport`
(`devtools.rs`). Панель — отдельный Svelte-роут, доступный только при `devtools`.

```rust
#[derive(Serialize)]
pub struct SiteTestReport {
    pub source_id: String,
    pub steps: Vec<StepResult>,   // name, ms, ok, detail
    pub titles_found: usize,
    pub chapters_found: usize,
    pub pages_found: usize,
    pub sample_page_urls: Vec<String>,
    pub first_page_preview_b64: Option<String>, // маленький PNG для UI
    pub detected_format: Option<String>,
    pub branches: Vec<String>,
    pub error: Option<String>,
}
```

## 2. `doctor` — health-чек всех источников

Один прогон по **всем** сайтам с лёгким запросом (`search("naruto", limit=1)`),
чтобы видеть, что ещё живо. Сайты-читалки часто ломаются — это ранний сигнал.

- CLI: `mangadl-cli doctor [--json]` → таблица `id | status | latency | ok/err`.
  Exit-код ≠ 0, если упал хоть один `verified`-источник (для nightly CI/алертов).
- GUI: вкладка «Здоровье источников» с той же таблицей + кнопка «перепроверить».
- Отличает ожидаемое (`stub` → skip, `unverified` → warn) от регресса
  (`verified` → fail).

## 3. CLI тест-подкоманды (headless, для CI)

```
mangadl-cli test-source <id> <query>   # полный pipeline одного сайта, exit code
mangadl-cli test-all [--verified-only]  # по всем, сводка + exit code
mangadl-cli record <id> <query>         # записать фикстуры (см. §4)
```

- `test-source` = headless-версия панели из §1 (тот же `SiteTestReport`, печатает JSON).
- Годится для `cron`/CI matrix: один сайт = один job, зелёный/красный по каждому.
- **Feature-gate живой сети:** сетевые тесты только при `--features live` или
  `MANGADL_LIVE=1`, иначе скипаются (CI по умолчанию офлайн).

## 4. Golden-фикстуры парсеров (офлайн, обязательный гейт)

Аналог текущего `tests/test_parsers.py`, но с записью реальных ответов.

- `fixtures/<source>/search.json`, `chapters.json`, `chapter_pages.json`,
  `mangahub_chapters.html` и т.п. — записаны командой `record` (§3) из живого API.
- Тест: скормить фикстуру парсеру источника (без сети) и проверить, что
  `SearchResult/ChapterInfo/PageInfo` разобрались как ожидается (snapshot/`insta`).
- Ловит регресс парсинга при рефакторинге и «дрейф» формата сайта (перезаписал
  фикстуру — diff показал, что изменилось у сайта).

```rust
#[test] // без сети
fn remanga_parses_search_fixture() {
    let raw = include_str!("../fixtures/remanga/search.json");
    let out = remanga::parse_search(raw).unwrap();
    assert_eq!(out[0].source_id, "remanga");
    assert!(out[0].chapters_count.is_some());
}
```

> Требование к порту: у каждого адаптера **выделить чистую `parse_*`-функцию**
> (без сети), принимающую сырой текст/JSON — чтобы её можно было тестировать на
> фикстуре. В Python это уже так (регэкспы/разбор отделимы) — сохранить.

Перенос текущих Python-тестов как ориентир паритета: `normalize_title`,
группировка, выбор best, `_num`, `_pick_title`, mangahub-регэкспы, remanga-flatten.

## 5. Mock-сервер: лимиты, ретраи, скачивание

`wiremock`-крейт поднимает локальный HTTP и проверяет **поведение движка** без
реальных сайтов:

- **429 + `Retry-After: N`** → клиент ждёт N и повторяет (порт `parse_retry_after`).
- **500/502/503/504** → экспоненциальные ретраи, затем ошибка.
- **Token-bucket** → не превышает заданный RPS (замер интервалов).
- **Downloader** → отдаёт байты картинки, проверяем сохранение/детекцию формата/
  конвертацию AVIF→JPEG и раскладку `original/`+`converted/`.
- **Пустые/битые страницы** → устойчивость (как «грязные данные» в Python).

Детерминированно, быстро, гоняется на каждый PR.

---

## 6. IPC-контракт тесты (Tauri ↔ фронт)

Каждая `#[tauri::command]` (см. ARCHITECTURE §8) — тест на форму входа/выхода
(serde round-trip), чтобы фронт и ядро не разъехались. `download_chapters`
проверяем на корректную последовательность событий прогресса (mock-ядро).

---

## 7. E2E смоук приложения

Перед релизом: собрать бинарь, поднять приложение (Tauri WebDriver /
`tauri-driver`), проверить критический путь: ввод запроса → результаты → выбор
тайтла → старт скачки → появились файлы. Один-два сценария, не больше — дорого и
флапно, поэтому только перед релизом, не на каждый PR.

---

## 8. Android: сборка + smoke на эмуляторе

Мобильная сборка тестируется отдельно, т.к. платформенные части (хранилище,
фоновая скачка, AVIF под NDK) в desktop-тестах не покрываются.

- **Сборка APK** (`cargo tauri android build`) в CI/локально — сам факт успешной
  сборки под `aarch64-linux-android` уже ловит непортируемые зависимости.
- **Smoke на эмуляторе** (Android emulator, headless в CI): установить APK,
  запустить, прогнать критический путь — поиск → тайтл → скачка 1 главы → файлы в
  app-dir. Проверить выбор папки (SAF) и что скачка переживает сворачивание
  (foreground-service).
- **Per-site тест-панель на устройстве.** Тот же QA-режим (§1) доступен в
  Android-сборке — можно на реальном телефоне прогнать конкретный сайт «в поле»
  (полезно: мобильные сети/IP иногда ведут себя иначе, чем десктопные).
- **AVIF на Android:** тест декода/отображения первой страницы AVIF-источника —
  подтверждает решение Фазы 1b (конвертация или оригинал-fallback).

Периодичность: перед релизом и при любых правках платформенного слоя
(`mangadl-tauri`, `OutputStorage`, AVIF). Не на каждый PR — дорого.

## Требования к CI

- **PR-гейт (обязателен, офлайн):** уровни 4, 5, 6, плюс `cargo clippy`,
  `cargo fmt --check` и **компиляция `mangadl-core` под `aarch64-linux-android`**
  (ловит непортируемые зависимости рано, без полной APK-сборки).
- **Nightly (сеть):** уровень 3 `test-all --verified-only` + `doctor` матрицей по сайтам;
  падение сайта → предупреждение/issue, не блок PR.
- **Перед релизом:** уровень 7 + сборка бинаря на чистой VM (DoD-6).
